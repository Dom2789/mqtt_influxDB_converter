How to use this

Five ground rules

1

Work the phases in order. Phases 1–3 need no broker and no database, so you can write most of this project offline, on a laptop, with nothing running.

2

Write the test before the code wherever a step says table-driven. The pure parts of this project — topic matching, decoding — are the best test-first practice in it, because the right answer is obvious and the implementation is not.

3

Keep the old code running until Step 17. main.py and src/ stay on disk and keep working while the new package grows beside them. Nothing is deleted until the replacement is proven.

4

Commit at every step boundary. Eighteen small commits make it possible to see which step broke something.

5

Signatures in this plan are the contract, not a style suggestion. The protocols in Phase 1 are what let Phase 4 and 5 be written without touching Phase 1 again.

02

The two core types and the error base

mqtt_influx_bridge/model.py mqtt_influx_bridge/errors.py tests/test_model.py
Approach
  1. Standard-library imports only: dataclass, datetime, Mapping. If you find yourself importing anything else, something belongs in a later step.
  2. errors.py imports nothing at all. Every later module imports from it, so it must stay at the bottom of the dependency graph.
  3. Stamp received_at with datetime.now(UTC). Not utcnow() — it is deprecated on 3.12 and hands back a naive value that will write points at the wrong time.
  4. Write the first test: build each type, then assert that assignment raises FrozenInstanceError.
  5. Expect a consequence in Step 12: because these are frozen, merging tags means dataclasses.replace(reading, tags=…), never assignment.

Two frozen dataclasses and no imports beyond the standard library. RawMessage is what arrives; Reading is what every later stage speaks.

@dataclass(frozen=True, slots=True)
class RawMessage:
    topic: str
    payload: bytes
    received_at: datetime          # UTC, stamped on arrival

@dataclass(frozen=True, slots=True)
class Reading:
    measurement: str
    fields: Mapping[str, float | int | str | bool]
    tags: Mapping[str, str]
    timestamp: datetime

Then errors.py: one root exception, and the first leaf under it. Later steps add siblings — a decode failure in Step 6, a config failure in Step 8 — but they all hang here.

class BridgeError(Exception):
    """Base for all expected, per-message failures in the bridge."""

class TagIndexError(BridgeError):
    """A [[sensor]] tag index doesn't fit the topic it was applied to."""
Why a root exception, and why not IndexError

Step 12 wraps each message in a try/except and drops the message on failure. That handler is only safe if the exception it catches means exactly one thing: a failure this bridge anticipates. except IndexError or except ValueError there would also swallow a genuine off-by-one or a stray float(payload) in your own pipeline code, silently dropping messages for a reason that has nothing to do with the data. except BridgeError cannot: anything unanticipated propagates and crashes loudly, which is what you want from a real bug. For the same reason TagIndexError must not subclass IndexError — the whole point is to sit outside the branch where accidental indexing bugs land.

Why

Reading is deliberately not an Influx Point. That single decision is what keeps decoders free of influxdb_client, which in turn is what makes them testable with a plain assert and makes a second sink cost nothing. payload stays bytes because decoding can fail, and a decoder that owns the decode can report that failure properly.

Verify

A test that constructs both and asserts FrozenInstanceError on assignment. Trivial, but it is your first green test. Add one line that pins the hierarchy — assert issubclass(TagIndexError, BridgeError) and assert not issubclass(TagIndexError, IndexError) — so a later refactor cannot quietly re-break Step 12's handler.

MQTT topic matching

mqtt_influx_bridge/routing.py tests/test_routing.py
Approach
  1. Put the table above into a parametrised test first and watch it fail. The rules are short enough to enumerate completely, which is what makes this the best test-first exercise in the project.
  2. Split both pattern and topic on / and walk the levels in step.
  3. + consumes exactly one level. # is legal only as the final level, and consumes every remaining level.

One function: topic_matches(pattern: str, topic: str) -> bool, implementing MQTT wildcard semantics. Write the test table first — the rules are short enough to enumerate, and two of them are easy to get wrong.

# pattern, topic, expected
("temp/techroom/1", "temp/techroom/1", True)
("temp/+/1",        "temp/techroom/1", True)
("temp/+",          "temp/techroom/1", False)   # + is exactly one level
("temp/#",          "temp/techroom/1", True)
("temp/#",          "temp",            True)    # # matches the parent too
("#",               "$SYS/broker/load", False)  # wildcards skip $-topics
("+/techroom/1",    "temp/techroom/1", True)
Trap

The two rules that catch people: temp/# matches the bare topic temp, and a leading wildcard never matches a topic beginning with $. Both are in the MQTT spec and both will bite you on a real broker.

04

Tags from topic levels

mqtt_influx_bridge/routing.py tests/test_routing.py
Approach
  1. Take the topic plus a {tag_name: level_index} mapping and return a plain dict[str, str].
  2. Split once, index into the levels, and keep every value a string — Influx tag values are strings by definition, so cast rather than hope.
  3. On an unusable index, raise TagIndexError from Step 2 rather than return a partial dict. Step 12 then logs it and drops that one message instead of writing a reading with a missing identity.
  4. Check index < 0 explicitly. Python's own bounds check only guards one end: levels[-1] does not raise, it returns the last level.
  5. Put the index, the tag name, the topic and the actual level count in the message. It is the only diagnostic the Step 12 log line will carry.

Add tags_from_topic(topic: str, mapping: Mapping[str, int]) -> dict[str, str], turning topic levels into tag values: with {"room": 1, "device": 2}, the topic temp/techroom/1 yields {"room": "techroom", "device": "1"}.

An unusable index must raise TagIndexError, which the pipeline can catch and log per message rather than crash the thread.

Trap

A negative index is the dangerous case, not the too-large one. {"room": 7} on a three-level topic raises on its own; {"room": -1} is a config typo that quietly tags room="1" and writes a wrong-but-plausible series into Influx forever. Nothing alerts and the points cannot be corrected afterwards, so the check is cheaper than the cleanup. The negative test depends only on the mapping, so Step 8 can also reject it at config load and fail at startup; the range check cannot move, because with temp/# the level count varies per message.

Why this earns its keep

This is the mechanism that makes one [[sensor]] block cover a whole fleet of identical devices. Without it, every new sensor is a new config block; with it, temp/+/+ plus two indices handles all of them. It is the main reason the project scales in sensor count.

Verify

Tests for the happy path, index 0, an index past the end of the topic, and a negative index — the last two both pytest.raises(TagIndexError).

Decoder protocol and registry

mqtt_influx_bridge/decoders/__init__.py mqtt_influx_bridge/decoders/base.py tests/test_decoder_registry.py
Approach
  1. A Protocol with the single decode method, plus a DecodeError that carries the topic and a short payload excerpt.
  2. A module-level dict and a register("name") class decorator that writes into it.
  3. get_decoder(name) raises on an unknown name, with the valid names sorted into the message.
  4. Import every decoder module from decoders/__init__.py. Registration only runs when the module is imported — miss this and the registry is empty at startup, which looks exactly like a config bug.

Define the protocol, a DecodeError, and a name registry so that config can select a decoder by string.

class Decoder(Protocol):                      # pure: no I/O
    def decode(self, msg: RawMessage, spec: SensorSpec) -> Iterable[Reading]: ...

_REGISTRY: dict[str, type[Decoder]] = {}

def register(name: str):                      # class decorator
    ...

def get_decoder(name: str) -> type[Decoder]:
    # unknown name -> raise, listing the valid options
Why a registry

So that a typo in config.toml fails at startup with the list of valid names, instead of at the first message that arrives at 3 a.m. Adding a payload format then costs one file, one decorator and one import — which is the whole point of the refactor.

Verify

Register a dummy decoder in a test, look it up, and assert that an unknown name raises with the valid names in the message.

06

The scalar decoder — replace the magic slice

mqtt_influx_bridge/decoders/scalar.py tests/test_decoders_scalar.py
Approach
  1. Decode the bytes to text, apply the extraction rule from the spec, cast the result, return one Reading.
  2. Three extraction modes: a bare number, a number followed by a unit, and an optional regex with one capture group for anything stranger.
  3. Compile the regex and reject bad options in __init__ rather than in decode. That is the move that turns a config typo into a startup error.
  4. Catch each failure and re-raise it as DecodeError. No ValueError or UnicodeDecodeError should ever escape this class.

This is the step that retires message.split(":")[1][:-1]. Extract one numeric value from a payload, with the extraction pattern coming from config rather than from code. Handle: a plain number (21.5), a number with a unit (21.5 °C), and an optional regex with a capture group for anything else.

Four failures to handle, not raise

Non-UTF-8 payload; no match in the payload; a match that will not cast to float; and an empty payload. Each must produce a DecodeError carrying the topic and a short payload excerpt — never a traceback. Validate bad decoder options at construction time, so a broken config dies at startup.

Verify

Feed it the real payload your sensor publishes and assert the exact Reading: measurement environment, field watertemperature, value 21.5. At this point the core of the old on_message is reproduced, correctly, under test, with zero network code written.

10

The Influx sink

mqtt_influx_bridge/sinks/influx.py tests/test_sink_influx.py
Approach
  1. Build the client and the write API once in __init__, and keep bucket and org as attributes.
  2. Convert Reading to Point in one small private method, setting the precision explicitly.
  3. Pass a WriteOptions covering the points below — all of it is library configuration, not code you write.
  4. close() closes the write API first, then the client. That order is what flushes the last batch.

One long-lived InfluxDBClient for the process lifetime, replacing the per-message client that cost a TCP — and with TLS, a handshake — per reading. Build the WriteApi with explicit WriteOptions.

  • Batch size and flush interval from InfluxWriteConfig.
  • max_retries with exponential backoff — the library's retry, not yours.
  • error_callback and retry_callback wired to the logger, or asynchronous write failures are invisible.
  • An explicit timestamp from RawMessage.received_at at nanosecond precision, rather than letting the server stamp it.
  • close() must flush. The batching API returns immediately, so an unflushed shutdown silently loses points.
Field type conflict

If the first point ever written for watertemperature carries an integer (21) and a later one a float (21.5), InfluxDB rejects the second for the whole series. This is what cast = "float" in the sensor config is for — and why it belongs in config rather than being inferred from whatever the first payload happened to look like.

Verify, without a database

Assert on the rendered line protocol string for a known Reading — measurement, tag set, field set and the explicit nanosecond timestamp. The real database comes in Step 16.

Phase 4

The pipeline

The middle of the diagram, and the heart of the reliability story: a bounded queue, a writer thread, and one try/except per message. Still no broker.

12

Router, queue, writer thread

mqtt_influx_bridge/pipeline.py tests/test_pipeline.py
Approach
  1. Build the Router once from the sensor specs, and instantiate one decoder per sensor at startup — not per message.
  2. submit() is the method paho's thread calls. It does one thing: put_nowait.
  3. The writer is a single threading.Thread(daemon=True) running the loop described below.
  4. Get the single-threaded path green first by calling the loop body directly from a test. Only start the thread once the logic is proven.

Build the router once at startup from the sensor specs. Note that match() returns all matching routes, not the first: a broad pattern and a specific one can legitimately both cover one topic.

class Router:
    def match(self, topic: str) -> list[Route]: ...
    def subscriptions(self) -> set[str]: ...   # deduplicated patterns

class Pipeline:
    def submit(self, msg: RawMessage) -> None: ...   # called from any thread
    def start(self) -> None: ...
    def stop(self, drain: bool = True) -> None: ...

Then the writer loop, which does all the work the old on_message did inline:

  • Take a RawMessage off the queue, find its routes, decode each one.
  • Merge tags: static tags from config, then tags_from_topic. Decoders contribute none.
  • Wrap each message in its own try/except BridgeError — the root from Step 2, not Exception. Log the topic and a payload excerpt, increment a counter, continue. One malformed message must never end the loop, and one unanticipated bug must never be mistaken for one.
  • Wrap each sink too: one failing sink must not stop the others from receiving the reading.
  • submit uses put_nowait and handles queue.Full by counting the drop and logging once per congestion episode — never by blocking. Blocking here would block the broker's network thread, which is the exact failure the queue exists to prevent.
Why the queue is not incidental

The old code called write_api.write() directly inside paho's callback, so an unreachable database stalled the MQTT loop. The queue is the seam that decouples broker speed from database speed. Pick the overflow policy deliberately: dropping newest is simple and keeps the producer free, and for telemetry it is usually right.

Verify — the tests that were impossible before

With a RecordingSink and direct submit() calls: exact readings arrive; tags merge in the right precedence; one wildcard sensor covers a fleet; one bad message does not stop the rest; a failing sink does not lose the others; queue.Full counts drops without raising; stop() drains. None of this was testable while subscribe() blocked forever in loop_forever().

13

Shutdown and counters

mqtt_influx_bridge/pipeline.py tests/test_pipeline.py
Approach
  1. stop() puts a sentinel on the queue, then join()s the writer thread with a timeout.
  2. Drain whatever is still queued, then close the sinks in reverse order of construction.
  3. Keep the counters as plain ints on the pipeline. The writer thread is their only writer, so no lock is needed — worth knowing why rather than adding one reflexively.
  4. Make a second stop() a no-op, because both a signal and a crash path may call it.

Finish stop(): signal the writer thread (a sentinel on the queue is the simplest correct method), drain what is queued, then flush and close every sink in order. Expose the counters you have been incrementing — messages in, readings out, decode errors, dropped — and log them once at shutdown.

Why order matters here

The unit is Restart=always, so this path runs on every deploy and every config change. Stop ingest first, then drain, then flush: any other order loses points. Those counters are also the only way you will ever notice a decoder quietly failing on 2% of messages.

Verify

Submit N messages, call stop() immediately, assert the recording sink received all N. Then assert a second stop() is harmless.

The source

Now the broker. One step, and the smallest file that touches the network — because reconnection is paho's job, not yours.

14

The paho source

mqtt_influx_bridge/sources/__init__.py mqtt_influx_bridge/sources/base.py mqtt_influx_bridge/sources/mqtt.py tests/test_source_mqtt.py
Approach
  1. Construct the client, assign the callbacks, and set the reconnect backoff — all in __init__, so start() has no decisions left to make.
  2. start() is connect_async + loop_start and returns immediately. stop() is loop_stop + disconnect.
  3. Hold the router's subscription set, not the sensor specs. The source needs nothing else from config, and keeping it that way is what makes it swappable.
class Source(Protocol):
    def start(self, on_message: Callable[[RawMessage], None]) -> None: ...
    def stop(self) -> None: ...

Keep on_message to two statements: stamp datetime.now(UTC) and hand the RawMessage to the callback. Nothing else belongs on the network thread.

  • reconnect_delay_set(min_delay, max_delay) for exponential backoff.
  • connect_async + loop_start instead of connect + loop_forever, so a broker that is down at startup is retried rather than fatal — and so start() returns and the process can own its own shutdown.
  • Issue subscribe() inside on_connect, using router.subscriptions(). The old code had this right; keep it. It is what makes a reconnect renew subscriptions automatically.
  • Log the reason code on on_connect and on_disconnect.
Verify, without a broker

Construct the source, then call its paho callbacks directly with a fake client and a stub message object. Drive the whole path — source, queue, writer, recording sink — and assert the reading arrives. Call on_connect twice and assert subscribe was called both times, which is the reconnect behaviour.

If you get stuck

Three places this plan is likely to bend

→

Step 8 is big. If the config loader starts to sprawl, split it: parse into dataclasses first, validate in a second pass. The tests stay the same either way.

→

Step 12 is the hard one. Threads plus error isolation plus tag merging in one file. If it fights you, get the single-threaded path green first — call the writer loop's body directly from a test — and only then start the thread.

→

Don't add asyncio. It will be tempting around Step 14. ARCHITECTURE.md has the full argument; the short version is that N sensors share one MQTT connection and one batched database connection, so there are two I/O endpoints whether N is 1 or 500. Revisit it only if sensors ever need active polling on independent timers.
