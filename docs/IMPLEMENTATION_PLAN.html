How to use this

Four ground rules

1

Work the phases in order. All of Phase 1 needs no broker and no database, so you can write most of this project offline, on a laptop, with nothing running.

2

Keep the old code running until Step 11. main.py and src/ stay on disk and keep working while the new package grows beside them. Nothing is deleted until the replacement is proven.

3

Commit at every step boundary. Eleven small commits make it possible to see which step broke something.

4

Signatures in this plan are the contract, not a style suggestion. Reading is the seam: because every stage speaks it and nothing but the sink knows what Influx is, Phases 2 and 3 can be written without reopening Phase 1.

Deliberately not here

Six things this plan does not build

An earlier draft ran to eighteen steps and carried a plugin registry, four Protocol classes, a bounded queue with its own writer thread, two decoders and four sinks. Each of the six cuts below has evidence beside it, because the point of writing them down is that none of them gets added back later on the grounds that the plan once called for it. If you want one back, get a measurement first.

→

No queue and no writer thread of your own. The batching WriteApi already is one. influxdb_client/client/write_api.py:259 builds a ThreadPoolScheduler(1) and a window_with_time_or_count pipeline, with a second scheduler at :114 and retry with jitter built in; write() pushes onto an rx Subject and returns. A queue in front of that is a third copy of the same mechanism. Step 07 has the full argument.

→

No scalar decoder. Both sensors publish JSON. The old message.split(":")[1][:-1] on {"temp":21.5} yields '21.5}' then '21.5' — the [:-1] was stripping the closing brace. One decoder covers everything you own.

→

No array indexing in the JSON decoder. The dotted-path half of this cut has been paid back — see Why dotted paths came back in Step 04: example_messages/power.txt is the measurement the cut asked for, and three real devices nest the fields that matter. Dict walking on . is in. What stays out is the all-digit-segment-as-index rule: the only arrays in those payloads are aenergy.by_minute and ret_aenergy.by_minute, and nothing wants a series out of them.

→

No hand-rolled topic matcher. paho ships one at paho/mqtt/client.py:423, topic_matches_sub(sub, topic). It agrees with the committed implementation on all seven cases in the old test table, including the two spec oddities that were the reason for writing one — the foo/# parent match and the $-topic rule.

→

No registry, and no protocols at all. One decoder needs no name lookup; two sinks need no Protocol to describe a write method; one source needs no interface. A Protocol is worth it when more than one body of code depends on the shape — extract it then, from real implementations rather than imagined ones.

→

No file sink, and no sub-packages. Logging goes to stdout and journald keeps it, so a second copy on disk earns nothing; --dry-run | tee covers the debugging case. The recording sink is a test double and lives in tests/conftest.py. decoders/, sinks/, sources/ and _lib/ become three modules and ten lines in __main__.py.

02

The core types and the error base

mqtt_influx_bridge/model.py mqtt_influx_bridge/errors.py tests/test_model.py

Frozen dataclasses, no imports beyond the standard library. RawMessage is what arrives; Reading is what every later stage speaks.

@dataclass(frozen=True, slots=True)
class RawMessage:
    topic: str
    payload: bytes
    received_at: datetime          # UTC, stamped on arrival

@dataclass(frozen=True, slots=True)
class Reading:
    measurement: str
    fields: Mapping[str, float | int | str | bool]
    tags: Mapping[str, str]
    timestamp: datetime

And errors.py, which imports nothing at all. Every later module imports from it, so it stays at the bottom of the dependency graph.

class BridgeError(Exception):
    """Base for all expected, per-message failures in the bridge."""

class TagIndexError(BridgeError):
    """A [[sensor]] tag index doesn't fit the topic it was applied to."""
Why a root exception, and why not IndexError

Step 07 wraps each message in a try/except and drops the message on failure. That handler is only safe if the exception it catches means exactly one thing: a failure this bridge anticipates. except IndexError or except ValueError there would also swallow a genuine off-by-one or a stray float(payload) in your own code, silently dropping messages for a reason that has nothing to do with the data. except BridgeError cannot: anything unanticipated propagates and crashes loudly, which is what you want from a real bug. For the same reason TagIndexError must not subclass IndexError — the whole point is to sit outside the branch where accidental indexing bugs land. The same rule binds DecodeError in Step 04.

Why Reading is not a Point

That single decision is what keeps the decoder free of influxdb_client, which in turn is what makes it testable with a plain assert and makes a second sink cost nothing. payload stays bytes because decoding can fail, and a decoder that owns the decode can report that failure properly. Because both types are frozen, merging tags in Step 07 means dataclasses.replace(reading, tags=…), never assignment.

The negative index, which is the real one

A negative index is the dangerous case, not the too-large one. {"room": 7} on a three-level topic raises on its own; {"room": -1} is a config typo that quietly tags room="1" and writes a wrong-but-plausible series into Influx forever. Nothing alerts and the points cannot be corrected afterwards. The explicit index < 0 check is in the committed code — keep it, and note that Step 05 can also reject it at config load, because it depends only on the mapping. The range check cannot move: with temp/# the level count varies per message.

Why this earns its keep

This is the mechanism that makes one [[sensor]] block cover a whole fleet of identical devices. The experiments branch does it by hand — msg.topic.split("/")[1:5] — which is the proof that the need is real. With temp/+/+ plus two indices, one block handles every device.

04

The JSON decoder

mqtt_influx_bridge/decoders.py tests/test_decoders.py mqtt_influx_bridge/model.py mqtt_influx_bridge/errors.py example_messages/power.txt mqtt_influx_bridge/decoders/
Approach
  1. First, two additions to earlier files: SensorSpec joins model.py, and DecodeError plus ConfigError join errors.py. Both are five-minute edits.
  2. json.loads the payload, then look up each key named in the spec's fields table. A key containing . is a path: key.split(".") and walk dicts, one get per segment. Dicts only — no list indexing.
  3. A segment that is missing, or that resolves to null, skips that field — it does not raise. This is now a decision, not a free choice; see Missing fields are skipped below. A payload that yields no fields at all produces no Reading.
  4. Cast every surviving value with the spec's cast, then return one Reading carrying all the fields, with tags left empty — Step 07 fills them.
  5. Validate the options in __init__, not in decode: the decoder is built once at config load in Step 05, so a broken spec is a startup error.
  6. Catch every failure and re-raise as DecodeError. No JSONDecodeError, ValueError, KeyError or UnicodeDecodeError may escape this class.

One class, two methods, one payload format — the one every sensor you own actually sends, the water probe and all three Shellys.

    def __init__(self, options: Mapping[str, Any]) -> None:
        ...        # reject bad options HERE, at startup
    def decode(self, msg: RawMessage, spec: SensorSpec) -> list[Reading]:
        ...        # tags stay empty; the handler merges them

That table is the shape the skip rule exists for: pf, temperature and counts each appear on some of the three devices and not the others, so a single [[sensor]] block with topic = "powermeter/+/+/status/+" and tags_from_topic = { room = 1, device = 2, channel = 4 } covers the whole rack, the strip's four channels and the esszimmer plug — and each point carries only the fields its device actually sent.

And the errors, in errors.py beside the other leaves. The base class is the part that matters:

class DecodeError(BridgeError):          # NOT ValueError — see Step 02
    def __init__(self, topic: str, payload: bytes, reason: str) -> None:
        self.topic, self.payload, self.reason = topic, payload, reason
        super().__init__(f"{topic}: {reason} (payload={payload[:40]!r})")

class ConfigError(BridgeError):
    """A config file that cannot produce a working bridge."""
One decoder, so no selection mechanism

There is nothing here to register, name or look up: Step 05 builds a JsonDecoder and Step 07 calls it. When a genuinely non-JSON sensor turns up, the second format costs one class in this file, a two-entry dict beside it, and a decoder = "…" key in SensorSpec — one small step, written down here so that it is not a surprise. What it does not cost is a decorator, a module registry or a Protocol: with two classes in one file, a dict literal is the whole mechanism, and it cannot be emptied by a linter dropping an import the way a registry can.

Where SensorSpec lives, and why

Put it in model.py, not config.py. config imports decoders to build the decoder at load time; if decoders imported SensorSpec back from config, that is a cycle, and you would be reaching for if TYPE_CHECKING: to paper over it. In model.py the graph stays a line — errors ← model ← decoders ← config — and no annotation needs quoting. It belongs there on merit too: it is a type every stage speaks, not a section of the config file.

Why dotted paths came back

The cut list says a cut returns only with a measurement behind it. example_messages/power.txt is that measurement: a Plug PM Gen3, a Power Strip 4 Gen4 and a Plug M Gen3, and every field worth keeping beyond the four flat electricals is nested — aenergy.total (the cumulative energy counter, on all three), temperature.tC, counts.on_time. A flat payload.get(key) cannot reach any of them, so the original rationale — "a nesting level neither sensor sends" — is simply no longer true of the hardware. The cost is one split(".") and a loop; the all-digit-index rule stays cut.

Missing fields are skipped

Choosing here is no longer free. The three devices publish overlapping but unequal field sets — pm1:0 has no pf, no output and no counts; only the Plug M reports temperature — so raise on a missing key means one wildcard [[sensor]] block cannot span them and you are back to one block per device model, which is exactly the fleet property tags_from_topic exists to provide. So: a missing segment or a null drops that field, silently, and the remaining fields are still written. Put that sentence in the decode docstring and pin it with a test, because the failure mode it trades into is the quiet one: a typo in fields now yields a point with fewer fields rather than an error. Step 05's unknown-key check does not help — the key names inside fields are arbitrary by design. The protection is the Step 07 counter plus --dry-run on a real topic once per new device.

Other failures to handle, not raise

A non-UTF-8 payload; an empty payload; a body that is not valid JSON; a body that is valid JSON but not an object; a value that will not cast. Every one must leave the class as a DecodeError carrying the topic and a short payload excerpt — never a traceback.

One cast per sensor, and what it buys

cast stays a single value for the whole sensor, which is what keeps a series type-stable against the conflict in Step 06. cast = "float" covers every numeric the three devices send, counts.on_time included. The price is that output (a JSON bool) lands as 0.0/1.0 rather than a boolean field, and that source or tag can never be selected at all. Accept that; if a boolean output is ever genuinely wanted, the cheap move is a second [[sensor]] block on the same topic with cast = "bool" and one field — not a per-field cast, which changes the config shape and every fields table in it.

Validate at load time, each as a ConfigError naming the field. Five are worth the code, because each one prevents either silent data corruption or a 3 a.m. failure:

  • An unknown key in any table, with the valid keys listed — the only one of the five that catches a silent mistake, since a typo'd tags key simply stops tagging.
  • A negative tags_from_topic index, per the trap in Step 03.
  • A malformed topic filter — # anywhere but the last level.
  • A non-string tag value, since Influx tag values are strings.
  • A missing credential in the environment, checked before the first connection attempt.
The one index you cannot check at startup

If a pattern ends in #, the topic length is unbounded, so no startup check can bound the index. Validate it where you can — a negative index always, a too-large index when the pattern has a fixed level count — and let the runtime check in tags_from_topic handle the rest as a per-message error. Knowing which invariants are checkable when is most of the skill in writing a config loader.

Do not raise KeyError from here

This file is full of dict access, so a KeyError escaping it is indistinguishable from a bug in the loader itself, and anything up the stack catching KeyError catches the wrong thing. It also mangles your message: KeyError.__str__ applies repr to its argument, so a careful sentence prints wrapped in quotes. Always re-raise as ConfigError with from None.

06

The two sinks

mqtt_influx_bridge/sinks.py tests/test_sinks.py tests/conftest.py mqtt_influx_bridge/sinks/ MQTT.file_output
Approach
  1. Both take a sequence of readings rather than one, so the Influx sink is free to batch. Both have write and close, and the contract lives in a docstring rather than a Protocol.
  2. StdoutSink prints one readable line per reading and is about five lines. It is what --dry-run swaps in.
  3. InfluxSink builds the client and the write API once in __init__, keeps bucket and org as attributes, and converts Reading to Point in one small private method with the precision set explicitly.
  4. close() closes the write API first, then the client. That order is what flushes the last batch.
  5. A RecordingSink that appends to a public list is the test instrument for Step 07 — put it in tests/conftest.py, not in the shipped module.

One long-lived InfluxDBClient for the process lifetime, replacing the per-message client that cost a TCP — and with TLS, a handshake — per reading. Build the WriteApi with explicit WriteOptions: batch size and flush interval from InfluxWriteConfig, max_retries with exponential backoff, and error_callback and retry_callback wired to the logger — without those last two, asynchronous write failures are invisible.

  • Stamp the point explicitly from RawMessage.received_at at nanosecond precision, rather than letting the server stamp it.
  • close() must flush. The batching API returns immediately, so an unflushed shutdown silently loses points.
Read the WriteOptions docs properly here

This is the step where the project's concurrency actually lives, and all of it is configuration rather than code you write — which is the reason Step 07 needs no thread. Getting batch_size, flush_interval, max_retries and retry_interval right is worth more than any code you could add in front of this sink.

Field type conflict

If the first point ever written for watertemperature carries an integer (21) and a later one a float (21.5), InfluxDB rejects the second for the whole series. This is what cast = "float" in the sensor config is for — and why it belongs in config rather than being inferred from whatever the first payload happened to look like. JSON makes this easy to trip over: {"temp":21} parses to an int.

Verify, without a database

capsys on the stdout sink. For the Influx sink, assert on the rendered line protocol string for a known Reading — measurement, tag set, field set, and the explicit nanosecond timestamp, with 21 rendering as 21.0. The real database comes in Step 10.

Phase 2

The bridge

Route a message to its sensors, decode it, merge its tags, hand it to the sinks — then connect the broker. Two steps, no threads of your own, and the first one still needs no network.

07

Router and message handler

mqtt_influx_bridge/bridge.py tests/test_bridge.py
Approach
  1. Build the Router first and test it alone. It holds the sensor specs and the decoders built in Step 05 — one decoder per sensor, at startup, never per message.
  2. match() uses paho's topic_matches_sub and returns all matching routes, not the first: a broad pattern and a specific one can legitimately both cover one topic.
  3. Then handle() — a plain function, called on paho's network thread, that does everything the old on_message did inline.
  4. Keep the counters as plain ints on a small dataclass. paho's loop_start runs one network thread, so handle has exactly one caller and no lock is needed — worth knowing why rather than adding one reflexively.
class Router:
    def match(self, topic: str) -> list[Route]: ...   # Route = spec + decoder
    def subscriptions(self) -> set[str]: ...          # deduplicated patterns

def handle(msg: RawMessage, router: Router,
           sinks: Sequence[Any], counters: Counters) -> None:
    ...

What handle does, in order:

  • Find the routes for the topic; for each, decode the payload.
  • Merge tags onto each reading: static tags from config, then tags_from_topic. The decoder contributes none, so this is the only place tags are set — and because Reading is frozen, that is dataclasses.replace.
  • Wrap the whole body in try/except BridgeError — the root from Step 02, not Exception. Log the topic and a payload excerpt, increment a counter, return. One malformed message must never kill the service, and one unanticipated bug must never be mistaken for one.
  • Wrap each sink call separately too: one failing sink must not stop the others from receiving the reading.
  • Count messages in, readings out, decode errors. Log the totals once at shutdown.
Why there is no queue and no writer thread

The old code's real bug was calling a synchronous write_api.write() inside paho's callback, so an unreachable database stalled the MQTT loop. The fix is the batching write API from Step 06, not a queue in front of it. Look at what you already depend on: influxdb_client/client/write_api.py:259 builds a ThreadPoolScheduler(1) and a window_with_time_or_count pipeline, with a second scheduler at :114 and retry-with-jitter built in, and write() pushes onto an rx Subject and returns. Your own queue plus writer thread would be a third copy of that machinery, and it would bring a sentinel, a join() timeout, a drain ordering and an overflow policy with it — all of it code that can only lose points, never gain them. For two sensors publishing every few seconds there is no throughput problem to solve here.

If you ever observe the MQTT loop actually stalling, that is the moment to add a queue — and you will have a number to size it with.

Verify — the tests that were impossible before

With the RecordingSink from conftest.py and direct handle() calls, no broker and no database: exact readings arrive; tags merge in the right precedence; one wildcard sensor covers a fleet; two overlapping patterns both fire; one bad message does not stop the next; a sink that raises does not lose the others; the counters add up. None of this was testable while subscribe() blocked forever in loop_forever().

08

The paho source

mqtt_influx_bridge/source.py tests/test_source.py mqtt_influx_bridge/sources/
Approach
  1. Construct the client, assign the callbacks, and set the reconnect backoff — all in __init__, so start() has no decisions left to make.
  2. start(on_message) is connect_async + loop_start and returns immediately. stop() is loop_stop + disconnect.
  3. Hold the router's subscription set, not the sensor specs. The source needs nothing else from config.
  4. One class, no protocol — there is one source. If a second ever appears (a serial reader, an HTTP poller), extract the interface then, from two real implementations rather than one imagined one.

Keep the paho callback to two statements: stamp datetime.now(UTC) into a RawMessage and pass it to the callback the caller handed start() — which in Step 09 is handle. Nothing else belongs in that function.

  • reconnect_delay_set(min_delay, max_delay) for exponential backoff.
  • connect_async + loop_start instead of connect + loop_forever, so a broker that is down at startup is retried rather than fatal — and so start() returns and the process can own its own shutdown.
  • Issue subscribe() inside on_connect, using router.subscriptions(). The old code had this right; keep it. It is what makes a reconnect renew subscriptions automatically.
  • Log the reason code on on_connect and on_disconnect.
Verify, without a broker

Construct the source, then call its paho callbacks directly with a fake client and a stub message object. Drive the whole path — source, handler, recording sink — and assert the reading arrives. Call on_connect twice and assert subscribe was called both times, which is the reconnect behaviour.

Wiring, CLI, signals, logging

mqtt_influx_bridge/__main__.py mqtt_influx_bridge/_lib/
Approach
  1. Parse args, load config, configure logging — in that order, so that --debug is already in effect if the config turns out to be broken.
  2. Build bottom-up: sinks, then router, then source — passing handle bound to the router, sinks and counters as the source's callback.
  3. Register the signal handlers so they only set a threading.Event, then block the main thread on event.wait(). Do no real work inside a handler.

Replace the Step 01 stub with the real main(): --config, --dry-run, --debug — a real ArgumentParser, which this repo has never had despite shipping a parser module.

  • Logging is about ten lines of logging.basicConfig straight in this file, defaulting to stdout so journald captures it. Do not carry src/_lib/logger.py or ConfigToml.py across — the first is replaced by those ten lines and the second by tomllib in Step 05. Delete the empty _lib/ package.

10

Integration: the eight checks

broker · InfluxDB config.toml
Approach
  1. Two terminals: the service in one, mosquitto_sub -h 192.168.1.225 -t '#' -v in the other, so you can see what the broker actually delivered versus what you wrote.
  2. Work straight down the list. Each line is a reliability claim that no unit test can reach.
  3. On the fleet check, publish against deliberately overlapping filters and count the writes. The MQTT spec lets a broker deliver one copy per matching subscription, so overlapping patterns can double-write; if yours does, subscribe to the minimal covering set instead.

Unit tests cannot cover any of these. Run them in order; the last one is the whole point of the refactor.

  • Dry run. --dry-run, then mosquitto_pub -h 192.168.1.225 -t temp/techroom/1 -m '{"temp":21.5}' — the decoded reading prints, nothing is written.
  • Real write. Same without --dry-run, then confirm in Influx: from(bucket:"…") |> range(start:-5m) |> filter(fn:(r) => r._measurement == "environment") shows watertemperature tagged room=techroom.
  • Database outage. Stop InfluxDB mid-run and publish: expect retry and backoff logs from the client's own retry_callback, no crash, and no stall in the MQTT loop. Restart it and confirm the buffered points land. This is the check that justifies having no queue of your own — if it fails, read WriteOptions again before writing any code.
  • Broker outage. Stop the broker mid-run: expect reconnect-backoff logs, then automatic resubscribe and resumed writes.
  • Garbage payload. -m 'garbage' — one warning naming the topic, service still alive. This is the failure that killed the old service.
  • Config typo. Add a misspelled key to a [[sensor]] block and start: expect a startup ConfigError naming the key and listing the valid ones, and no connection attempt.
  • Fleet. A wildcard sensor with tags_from_topic across several device numbers, published to in turn.
  • The goal. Add the Shelly power meter from the experiments branch as a [[sensor]] block on powermeter/+/+/status/+, with the three flat fields from Step 04. Restart. Confirm both measurements write over the same five-minute window.
What the last check demonstrates

A whole second sensor, on a different topic shape, added in a configuration file, with no Python written and no fork of the repo. That is the thing the old design could not do — and the reason the experiments branch existed. You can delete it once this passes.

Verify

All eight pass against live infrastructure, and uv run pytest is still green.

If you get stuck

Three places this plan is likely to bend

→

Step 05 is the big one now. It is the longest file and the only step with real breadth. If the config loader starts to sprawl, split it: parse into dataclasses first, validate in a second pass. The tests stay the same either way.

→

If writes feel slow, read WriteOptions before writing code. Every instinct will say to put a queue in front of the sink. The library already has one, two worker threads and retry with backoff; a queue of your own adds a sentinel, a drain and an overflow policy, and can only lose points. Add it when the database-outage check in Step 10 actually shows the MQTT loop stalling, and size it from that measurement.

→

Don't add asyncio. It will be tempting around Step 08. ARCHITECTURE.md has the full argument; the short version is that N sensors share one MQTT connection and one batched database connection, so there are two I/O endpoints whether N is 1 or 500. Revisit it only if sensors ever need active polling on independent timers.
